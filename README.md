# SNOWa

**Surveillance of Novel Outbreaks in Wastewater**

SNOWa is a reproducible Snakemake workflow for processing, quality checking, visualizing, and reporting SARS-CoV-2 wastewater genomic surveillance data.

## Overview

SNOWa integrates:

* Freyja lineage proportion estimates
* Wastewater sample-site metadata
* Site-associated population information
* SARS-CoV-2 lineage classifications
* Geographic boundary data

These inputs are used to produce jurisdiction-wide and county-level population-weighted lineage proportions, quality-control results, surveillance figures, and wastewater genomic surveillance reports.

### Scope

SNOWa begins with SARS-CoV-2 lineage proportion estimates generated by Freyja. Raw sequencing-data processing and Freyja deconvolution occur before data are added to SNOWa.

The workflow supports:

* Quality control of newly received run data
* Integration of new and historical run data
* Addition of sample-site and lineage-classification metadata
* Jurisdiction-wide and county-level population weighting
* Timeframe-specific data filtering
* Surveillance figure generation
* Markdown, HTML, and PDF report generation

Although the current workflow uses a field named `county`, agencies may use the corresponding county, county-equivalent, or administrative reporting area for their jurisdiction. Geographic names must remain consistent across the site metadata, boundary files, and non-sampled-area file.

SNOWa is intended to make routine processing and reporting reproducible. Successful workflow execution does not replace manual review or epidemiological interpretation.

### Workflow Summary

![SNOWa workflow overview](images/snowa_workflow.png)

![SNOWa Snakemake DAG](images/snowa_dag.svg)

SNOWa performs the following major steps:

1. Runs preliminary quality-control checks on new run files.
2. Moves files that pass Pre-QC into the historical run directory.
3. Merges historical run files.
4. Performs metadata quality control.
5. Adds sample-site and lineage-classification information.
6. Evaluates lineage mappings.
7. Calculates jurisdiction-wide and county-level population-weighted proportions.
8. Performs QC on weighted results.
9. Filters data for surveillance figures.
10. Generates surveillance figures and reports.
11. Compiles quality-control results.

## Getting Started

Getting started with SNOWa has two stages:

1. Install the required software and verify SNOWa using the included mock dataset.
2. Configure SNOWa with the surveillance, reference, geographic, and reporting files required by your program.

### Requirements

Install:

* [Git](https://git-scm.com/) to clone the repository
* [Snakemake](https://snakemake.github.io/) 7.32.4 or later
* [Apptainer](https://apptainer.org/docs/admin/main/installation.html) 1.4.5 or later

SNOWa requires a Linux environment.

Supported environments include:

* Ubuntu Linux
* Windows 10 or 11 using WSL2 with Ubuntu
* macOS using a Linux virtual machine

Windows users should run SNOWa from within WSL2/Ubuntu rather than directly from Windows.

### 1. Clone the Repository

```bash
git clone https://github.com/NW-PaGe/SNOWa
cd SNOWa
```

### 2. Verify the Installation

Run the included mock dataset before configuring SNOWa with surveillance data:

```bash
snakemake --cores 2 --use-singularity --configfile mock/mock_config.yaml
```

The mock configuration and dataset allow the complete workflow to be tested without agency surveillance inputs.

A successful run creates a `results/` directory containing workflow outputs, including QC results, processed data, figures, and reports.

After the mock workflow completes successfully, continue with the surveillance setup below.

### Container Environment

The SNOWa software environment is available from Docker Hub:

* [SNOWa Docker Hub repository](https://hub.docker.com/r/lunnwa/snowa)
* Image: `lunnwa/snowa:latest`

The default configuration identifies the image as:

```yaml
containerized: "docker://lunnwa/snowa:latest"
```

The published container is based on Ubuntu 22.04 and contains the software dependencies required by the SNOWa workflow.

Container source files are available at:

* [SNOWa container source repository](https://github.com/DOH-SML1303/customed-docker)

Routine users do not need to build or maintain the container.

## Initial Setup for Surveillance Data

After successfully running the mock dataset, configure the following resources.

| Resource                    | Default location                          | Purpose                                                   |
| --------------------------- | ----------------------------------------- | --------------------------------------------------------- |
| New run data                | `new_runs/`                               | Newly received Freyja lineage estimates                   |
| Historical run data         | `runs/`                                   | Previously accepted run files                             |
| Sample-site metadata        | `defaults/sample_site-counties.csv`       | Connects sample sites to geographic areas and populations |
| Lineage Classification File | `defaults/ww_lineage_classifications.csv` | Maps Freyja lineages to wastewater reporting categories   |
| Geographic boundary files   | `defaults/`                               | Provides boundaries for surveillance maps                 |
| Non-sampled-area file       | `defaults/non_sampled_counties.csv`       | Identifies areas without sampled wastewater sites         |
| Configuration file          | `defaults/config.yaml`                    | Defines workflow paths and reporting settings             |
| Report template             | `defaults/report.md`                      | Defines the surveillance report structure                 |

### 1. Obtain the Wastewater Lineage Classification File

Download:

* [`results/ww_lineage_classifications.csv`](https://github.com/NW-PaGe/lineage-classification-cdc/blob/main/results/ww_lineage_classifications.csv)

from the:

* [Lineage classification repository](https://github.com/NW-PaGe/lineage-classification-cdc)

Save the file as:

```text
defaults/ww_lineage_classifications.csv
```

### 2. Create the Sample-Site Metadata

Create:

```text
defaults/sample_site-counties.csv
```

Required columns:

| Column        | Description                                                       |
| ------------- | ----------------------------------------------------------------- |
| `Sample_Site` | Sample-site identifier matching the run data                      |
| `county`      | Geographic reporting area associated with the sample site         |
| `population`  | Population associated with the sample site and used for weighting |

Example:

```text
Sample_Site,county,population
A,King County,245487
```

The current schema requires the field name `county`, even if another county-equivalent or administrative area is used.

Multiple sample sites may belong to the same geographic area.

### 3. Obtain Geographic Boundary Files

SNOWa requires geographic boundary data for surveillance maps.

Use an authoritative source appropriate for the jurisdiction. For U.S. agencies, county and county-equivalent boundaries are available from the [U.S. Census Bureau TIGER/Line Shapefiles](https://www.census.gov/geographies/mapping-files/time-series/geo/tiger-line-file.html).

Place the complete boundary dataset in:

```text
defaults/
```

Geographic area names must match the values used in:

* `defaults/sample_site-counties.csv`
* `defaults/non_sampled_counties.csv`

The current map workflow expects a geographic field identifying the reporting area. See the SNOWa wiki for detailed geographic-data requirements.

### 4. Create the Non-Sampled-Area File

Create:

```text
defaults/non_sampled_counties.csv
```

Required column:

```text
non_sampled_county
```

Example:

```text
non_sampled_county
Example County
```

Use the same geographic naming format used in the sample-site metadata and boundary files.

### 5. Review the Configuration

Open:

```text
defaults/config.yaml
```

Review and update:

* Input and reference-file paths
* Geographic-data paths
* Plot timeframes
* Report metadata
* Container configuration, if needed

### 6. Review the Report Template

Open:

```text
defaults/report.md
```

Review the report structure and organization-specific language before generating the first surveillance report.

## Required Run Data

### New Run Data

Place newly received run files in:

```text
new_runs/
```

Run data files must be tab-separated (`.tsv`).

Metadata and reference files used by SNOWa are comma-separated (`.csv`).

SNOWa currently expects run data in the tabular format generated by the existing Freyja post-processing workflow.

A file may contain data from one or multiple sequencing runs as long as all required fields are present.

### Required Columns

| Column                   | Type       | Description                                                | Example      |
| ------------------------ | ---------- | ---------------------------------------------------------- | ------------ |
| `Lab_ID`                 | Text       | Laboratory or sequencing-run identifier                    | `LAB0000001` |
| `Sample_ID`              | Identifier | Wastewater sample identifier                               | `1000000`    |
| `Sample_Collection_Date` | Date       | Sample collection date in `YYYY-MM-DD` format              | `2024-06-05` |
| `Sample_Site`            | Text       | Sample-site identifier matching the site metadata          | `G`          |
| `Variant_name`           | Text       | Freyja-estimated Pango lineage or accepted result category | `LB.1`       |
| `Variant_proportion`     | Numeric    | Estimated proportion of the lineage within the sample      | `0.3958465`  |

County and ZIP-code information should not be included in the run file. Geographic information is added from the sample-site metadata.

Accepted non-Pango `Variant_name` categories include:

* `ancestral`
* `recombinant`
* `unreportable`

### Minimal Example

```text
Lab_ID      Sample_ID   Sample_Collection_Date  Sample_Site  Variant_name  Variant_proportion
LAB0000001  1000000     2024-06-05              G            LB.1          0.3958465
LAB0000001  1000000     2024-06-05              G            KP.3          0.20178339
```

### Basic Validation Requirements

New run files are evaluated for issues including:

* Missing required values
* Date formatting
* Sample-date recency
* Duplicate records
* Unrecognized sample sites
* Invalid lineage proportions
* Metadata-formatting problems

`Sample_Collection_Date` must use `YYYY-MM-DD`.

`Variant_proportion` must contain numeric values between 0 and 1.

A `Sample_ID` may appear on multiple rows because each row represents one lineage estimate for the sample.

For each sample, `Variant_proportion` values should sum to 1.

Files containing hard QC issues remain in `new_runs/` until the identified problems are corrected.

Detailed QC rules and failure conditions are documented in the SNOWa wiki.

### Historical Run Data

Historical run files are stored in:

```text
runs/
```

Historical files must use the same structure as new run data.

Files that pass Pre-QC are automatically moved from `new_runs/` to `runs/`.

## Reference Files

### Sample-Site Metadata

The configured file is:

```text
defaults/sample_site-counties.csv
```

Update this file when:

* A new sample site is added
* A site's geographic assignment changes
* A site population estimate changes

The updated metadata are used the next time SNOWa runs.

Detailed population-weighting methods and population-estimate guidance are documented in the SNOWa wiki.

### Wastewater Lineage Classification File

SNOWa uses:

```text
defaults/ww_lineage_classifications.csv
```

Primary fields used by SNOWa include:

| Column                    | Purpose                                                               |
| ------------------------- | --------------------------------------------------------------------- |
| `lineage_extracted`       | Lineage matched to wastewater results                                 |
| `wastewater_variant_name` | Wastewater reporting category                                         |
| `hex_code`                | Color associated with the reporting category                          |
| `status`                  | Optional lineage status used when resolving duplicate classifications |

The LCF should be checked for updates before processing a new run.

If a lineage cannot be mapped, review the lineage-mapping QC results before continuing.

Local additions to the LCF are supported.

### Non-Sampled Areas

The configured file is:

```text
defaults/non_sampled_counties.csv
```

Update this file whenever geographic sampling coverage changes.

### Report Template

The report template is:

```text
defaults/report.md
```

It is used to generate:

```text
results/ww_report.md
results/ww_report.html
results/ww_report.pdf
```

## Configuration

The primary configuration file is:

```text
defaults/config.yaml
```

### Common Paths

| Configuration key                       | Default value                             | Purpose                                        |
| --------------------------------------- | ----------------------------------------- | ---------------------------------------------- |
| `pre_qc.directory`                      | `new_runs/`                               | Newly received run files                       |
| `merge_data.directory`                  | `runs/`                                   | Historical run files                           |
| `add_sites_and_classes.sites`           | `defaults/sample_site-counties.csv`       | Site, geographic-area, and population metadata |
| `add_sites_and_classes.classifications` | `defaults/ww_lineage_classifications.csv` | Wastewater Lineage Classification File         |
| `geographic_data.shapefiles_dir`        | `defaults/`                               | Geographic boundary files                      |
| `geographic_data.non_sampled_counties`  | `defaults/non_sampled_counties.csv`       | Areas without sampled sites                    |
| `plots.plot_dir`                        | `results/plots/`                          | Generated surveillance figures                 |

### Plot Timeframes

Each surveillance figure has an independently configured timeframe.

A timeframe may use either:

* A relative `recency` period, or
* A fixed `date_range`

For example:

```yaml
stacked_bar_plt:
  timeframe:
    recency:
      value: 1
      unit: year
```

or:

```yaml
stacked_bar_plt:
  timeframe:
    date_range:
      start_date: 2024-01-01
      end_date: 2024-06-30
```

Supported recency units are:

* `day` / `days`
* `week` / `weeks`
* `month` / `months`
* `year` / `years`

Use either `recency` or `date_range` for an individual figure.

### Report Metadata

Review the `report` section before generating a new report:

```yaml
report:
  format: "pdf"
  date: "[Report date]"
  report_generator: "[Name and credentials]"
  report_generator_team: "[Team or program]"
  interpretations_by: "[Name and credentials]"
  interpretations_by_team: "[Team or program]"
  data_period: "[Reporting period]"
```

# Routine Implementation

After initial setup is complete, use the following process for routine surveillance runs.

## 1. Add New Run Data

Place the new Freyja lineage proportion file in:

```text
new_runs/
```

Confirm that the file:

* Is tab-separated
* Contains all required columns
* Uses valid sample-site identifiers
* Does not contain county or ZIP-code fields

## 2. Update the Wastewater Lineage Classification File

Check the:

* [Lineage classification repository](https://github.com/NW-PaGe/lineage-classification-cdc)

for an updated:

* [`results/ww_lineage_classifications.csv`](https://github.com/NW-PaGe/lineage-classification-cdc/blob/main/results/ww_lineage_classifications.csv)

Save the current file as:

```text
defaults/ww_lineage_classifications.csv
```

## 3. Update Site and Geographic Files When Needed

Update `defaults/sample_site-counties.csv` when:

* A new site is added
* A site's geographic assignment changes
* A population estimate changes

Update `defaults/non_sampled_counties.csv` when sampling coverage changes.

Update geographic boundary files when the underlying geographic reference data change.

## 4. Review the Configuration

Before running SNOWa, review:

* Input and reference-file paths
* Plot timeframes
* Report date
* Reporting period
* Report author and interpretation fields

## 5. Run Pre-QC

Run:

```bash
snakemake pre_qc --cores 1 --use-singularity
```

The Pre-QC report is written to:

```text
results/qc/pre_qc_report.txt
```

Review the report before continuing.

If the new files pass Pre-QC, they are automatically moved from:

```text
new_runs/
```

to:

```text
runs/
```

If issues are detected, the files remain in `new_runs/`.

Correct the identified problems and rerun Pre-QC. Files are not added to the historical run directory until Pre-QC passes.

## 6. Run the Complete Workflow

Run:

```bash
snakemake --cores <N> --use-singularity
```

The complete workflow generates:

* Quality-control results
* Combined and enriched datasets
* Jurisdiction-wide and county-level population-weighted proportions
* Figure-specific filtered datasets
* Surveillance figures
* Markdown, HTML, and PDF reports

## 7. Review Quality-Control Results

At minimum, review:

```text
results/qc/pre_qc_report.txt
results/qc/metadata_qc_raw.txt
results/qc/lineage_mapping_qc_report.txt
results/qc/weighted_proportions_qc_report.txt
results/qc/weekly_county_report.txt
results/full_qc_report.html
results/plots/qc_pa_plt.jpeg
```

Correct identified issues and rerun affected workflow steps before interpreting or distributing results.

Detailed definitions, warnings, failure conditions, and QC interpretation are documented in the SNOWa wiki.

### Re-Run a Specific Output

Snakemake can regenerate an individual output and its required dependencies.

Examples:

```bash
snakemake results/plots/heatmap_plt.jpeg --cores <N> --use-singularity
```

```bash
snakemake results/full_qc_report.html --cores <N> --use-singularity
```

```bash
snakemake results/ww_report.pdf --cores <N> --use-singularity
```

## Quality Control

SNOWa performs quality control at multiple stages, including:

* Preliminary QC of newly received run data
* Metadata QC after historical data are combined
* Lineage-classification mapping QC
* Population-weighting QC
* Weekly geographic/map review

The primary QC outputs are compiled into:

```text
results/full_qc_report.html
```

See the SNOWa wiki for:

* Individual QC checks
* Warning and failure conditions
* Numeric tolerances
* Lineage-mapping interpretation
* Population-weighting validation
* Weekly map review guidance

## Manual Review and Interpretation

All processed results, figures, and reports should be reviewed before distribution or interpretation.

Review should include:

* Expected sample sites and reporting periods
* QC warnings or failures
* Lineage-classification issues
* Population-weighted estimates
* Current geographic sampling coverage
* Consistency between figures and underlying data
* Whether written interpretations are supported by the surveillance results

SNOWa is intended to make reporting reproducible, not automatic.
